# SolYan PDF V1.8 — WebDAV Storage Adapter

Status: implementation branch `feat/v1.8-webdav-storage`.

## Goal

Extend the V1.7 Cloud Storage workspace with a self-hosted WebDAV lane without exposing WebDAV credentials to browser code and without changing the existing Google Drive / OneDrive OAuth behavior.

## Architecture

WebDAV is implemented as a concrete route-compatible adapter under `/storage/webdav/...` and is registered before the existing dynamic `/storage/{provider_id}/...` Cloud Storage router.

The browser continues to use the same user-visible operations:

- browse folders and PDFs;
- download a PDF;
- upload a new PDF;
- explicitly replace an existing PDF;
- disconnect the browser session.

WebDAV uses operator-owned server configuration rather than end-user OAuth. The browser's **Connect WebDAV** action creates only an opaque HttpOnly SolYan session marker. `WEBDAV_USERNAME` and `WEBDAV_PASSWORD` never leave the backend.

## Configuration

Required for the provider to report `configured=true`:

- `WEBDAV_BASE_URL`
- `WEBDAV_USERNAME`
- `WEBDAV_PASSWORD`

Optional:

- `WEBDAV_VERIFY_TLS=1` by default;
- `WEBDAV_ALLOW_INSECURE_HTTP=0` by default.

`WEBDAV_BASE_URL` must point at the collection root SolYan may access. HTTPS is required unless the operator explicitly enables insecure HTTP for a trusted local/test server.

## Security boundaries

- WebDAV credentials remain server-side and are never returned by status or file APIs.
- The browser session uses an HttpOnly cookie and the same bounded Cloud Storage session TTL policy.
- Mutation routes enforce the configured browser Origin allow-list.
- Provider redirects are disabled for WebDAV requests, preventing credentials from following an unexpected redirect to another host.
- Server-returned WebDAV `href` values must stay on the configured origin and under the configured collection root.
- Browser-visible item IDs are URL-safe opaque encodings of normalized paths; raw server paths are not accepted as route IDs.
- Path normalization rejects `.` / `..`, backslashes, NUL and CR/LF path segments.
- Only PDF objects are surfaced as files; downloads and uploads validate the `%PDF-` header and the shared Cloud Storage file-size bound.
- Upload-new checks for an existing destination and sends `If-None-Match: *`; an existing file returns conflict instead of being silently overwritten.
- Overwrite is available only through the explicit `/replace` operation already confirmed by the Cloud Storage UI.
- Provider response bodies are not reflected verbatim to the browser on failures.

## Compatibility

The adapter uses standard WebDAV methods only:

- `PROPFIND` with `Depth: 1` for browsing;
- `PROPFIND` with `Depth: 0` for existence checks;
- `GET` for download;
- `PUT` for upload / explicit replace.

The parser consumes DAV multistatus XML (`DAV:` namespace) and reads `displayname`, `resourcetype`, `getcontentlength`, `getlastmodified` and `getcontenttype`.

## V1.8 acceptance gate

The deterministic mock-WebDAV regression must verify:

1. configured/disconnected status before a browser session;
2. HttpOnly server session creation without exposing username/password;
3. folder + PDF listing while filtering non-PDF files;
4. opaque path IDs;
5. PDF download;
6. upload-new with no silent overwrite;
7. explicit replace;
8. mutation Origin guard;
9. logout/session removal;
10. frontend production build with Google Drive + OneDrive + WebDAV provider typing.

Real WebDAV servers remain deployment diagnostics because server implementation, authentication policy and TLS certificates are operator-controlled external inputs.
