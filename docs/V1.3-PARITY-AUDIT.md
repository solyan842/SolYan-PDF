# SolYan PDF V1.3 Parity Audit

## Scope

V1.3 continues the OSS-first parity policy after the self-contained V1.2 release. New work must close a concrete capability gap, prefer an existing SolYan engine or maintained upstream before adding dependencies, and keep provider/credential-dependent product families outside the self-contained core unless a product decision explicitly brings them in.

## Completed

### Remove Digital Signatures

Status: **implemented and regression-gated**.

SolYan PDF now provides `POST /pdf/remove-signatures` and a frontend tool at `/remove-signatures`.

The implementation uses the existing qpdf JSON structural pipeline rather than introducing a new PDF engine. It:

- walks AcroForm field trees, including inherited `/FT` values, and removes `/Sig` fields;
- removes signature Widget annotations from page `/Annots` while preserving non-signature form fields;
- removes the indirect signature `/V` payload references and rewrites the PDF so orphan signature/certificate objects are not retained as reachable document state;
- removes signature-related catalog permission references (`/DocMDP`, `/UR`, `/UR3`) and `/DSS` when present;
- preserves ordinary AcroForm fields;
- returns an unsigned input byte-for-byte when no signature-related state is found;
- validates rewritten output with `qpdf --check`.

The dedicated CI gate creates a real PKCS#12 fixture, signs the PDF through SolYan's existing pyHanko service, verifies one cryptographically valid embedded signature before processing, removes it through the production API, checks that a normal text field survives, checks that signature markers are absent from expanded PDF structure, and verifies through pyHanko that the result contains zero embedded signatures.

#### OSS reference

Stirling-PDF was reviewed as the maintained parity reference for this capability. Its current PDFBox path flattens top-level signature fields. SolYan keeps the same user-level capability while using the repository's existing qpdf/pyHanko stack and explicitly covers nested AcroForm structure and signature-specific catalog state.

#### Product boundary

This tool intentionally creates a new PDF that is no longer digitally signed. It does not validate signer identity or certificate trust; that remains the job of **Verify Signature**. It does not decrypt password-protected PDFs without valid credentials and is not intended to bypass PDF access permissions.

### PDF Inspector / Get ALL Info

Status: **implemented and regression-gated**.

Stirling-PDF's maintained `get-info-on-pdf` capability was reviewed as the parity reference. SolYan closes the same product gap without adding a new PDF engine: the backend image already contains qpdf and Poppler utilities.

SolYan's `POST /pdf/info` and `/pdf-info` UI combine:

- Poppler `pdfinfo` for user-facing document and metadata fields;
- `pdffonts` and `pdfimages -list` for bounded font/image inventories;
- qpdf JSON traversal from the catalog root for reachable structural counts, including pages, streams, object types, Image/Form XObjects, AcroForm fields, signature fields, embedded files, optional-content groups, outlines, XFA, actions and active annotations;
- qpdf encryption inspection for encryption state and permission summaries;
- SHA-256 and byte size for input identity;
- password support for encrypted PDFs, with invalid credentials rejected rather than silently returning a partial report.

Safety and boundedness rules:

- 100 MB upload ceiling shared with the backend PDF surface;
- at most 100,000 reachable qpdf objects are traversed;
- font/image table output is capped at 500 rows per category and reports truncation;
- PDF-origin metadata is returned as data and rendered through ordinary React text nodes; the UI does not use `innerHTML` or `dangerouslySetInnerHTML`;
- the inspector is read-only and does not claim malware detection or complete semantic validation.

The dedicated gate generates a real PDF containing a font, raster Image XObject, ordinary AcroForm field, signature field, embedded attachment, JavaScript OpenAction and deliberately HTML-shaped metadata. It checks qpdf/Poppler output, production API aggregation, exact metadata preservation through the JSON API, safe frontend wiring, encrypted-PDF inspection with the correct password, invalid-password rejection, and always uploads diagnostic logs. Backend CI, Frontend CI and the dedicated PDF Info Inspector CI all passed on the accepted feature implementation before this audit status was promoted.

### Unlock PDF Forms

Status: **implemented and regression-gated**.

Stirling-PDF's maintained `unlock-pdf-forms` controller was reviewed as the parity reference. Its behavior clears the PDF field ReadOnly bit, removes field `/Lock` entries, sets AcroForm appearances as needed and best-effort rewrites XFA `access="readOnly"` to `access="open"`.

SolYan uses the existing qpdf JSON engine rather than adding PDFBox or another PDF library. The implementation:

- traverses bounded AcroForm `/Fields` and `/Kids`, rejects cycles and limits depth/node count;
- clears only bit 1 (ReadOnly) from `/Ff`, preserving every other field flag and the existing field value;
- removes `/Lock` entries without flattening or deleting fields;
- keeps already-writable/no-form PDFs byte-identical;
- discovers only XFA streams referenced by the AcroForm, exports those streams individually with generalized decoding and rewrites `access="readOnly"` to `access="open"`;
- caps XFA at 256 referenced streams and 10 MB decoded per stream rather than decoding every content stream in the document;
- sets `/NeedAppearances` only when an actual form/XFA change occurs;
- validates rewritten output with `qpdf --check`.

The dedicated gate includes a field with ReadOnly plus an unrelated multiline flag, preserved field values, a `/Lock` dictionary, a Flate-compressed XFA packet containing multiple read-only attributes, a byte-identical writable no-op fixture, field-tree cycle rejection and qpdf validity. The UI explicitly separates this capability from password decryption: encrypted PDFs must first be decrypted with a valid password using the existing Unlock PDF tool. Backend CI, Frontend CI and the dedicated Unlock PDF Forms CI all passed on the accepted feature implementation before this audit status was promoted.

## Deferred / known boundaries

- Remove Images still targets Image XObjects. Inline content-stream images (`BI … ID … EI`) remain an explicit boundary because robust support would require a content-stream parser/dependency expansion rather than a small qpdf JSON mutation.
- Multi-party/remote signing, cloud connectors, AI summarization and translation remain provider/credential/product decisions rather than self-contained engine gaps.

## V1.3 acceptance rule

A new V1.3 capability is accepted only when its production route/UI is wired, real regression coverage passes on the exact branch HEAD, and no weaker fallback silently changes the documented semantics.
