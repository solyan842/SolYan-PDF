# SolYan PDF V1.3 Parity Audit

## Scope

V1.3 continues the OSS-first parity policy after the self-contained V1.2 release. New work must close a concrete capability gap, prefer an existing SolYan engine or maintained upstream before adding dependencies, and keep provider/credential-dependent product families outside the self-contained core unless a product decision explicitly brings them in.

## Completed

### Remove Digital Signatures

Status: **implemented and regression-gated**.

SolYan PDF now provides `POST /pdf/remove-signatures` and a frontend tool at `/remove-signatures`.

The implementation uses the existing qpdf JSON structural pipeline rather than introducing a new PDF engine. It:

- walks AcroForm field trees, including inherited `/FT` values, and removes `/Sig` fields;
- removes signature Widget annotations from page `/Annots` while preserving non-signature form fields;
- removes the indirect signature `/V` payload references and rewrites the PDF so orphan signature/certificate objects are not retained as reachable document state;
- removes signature-related catalog permission references (`/DocMDP`, `/UR`, `/UR3`) and `/DSS` when present;
- preserves ordinary AcroForm fields;
- returns an unsigned input byte-for-byte when no signature-related state is found;
- validates rewritten output with `qpdf --check`.

The dedicated CI gate creates a real PKCS#12 fixture, signs the PDF through SolYan's existing pyHanko service, verifies one cryptographically valid embedded signature before processing, removes it through the production API, checks that a normal text field survives, checks that signature markers are absent from expanded PDF structure, and verifies through pyHanko that the result contains zero embedded signatures.

### OSS reference

Stirling-PDF was reviewed as the maintained parity reference for this capability. Its current PDFBox path flattens top-level signature fields. SolYan keeps the same user-level capability while using the repository's existing qpdf/pyHanko stack and explicitly covers nested AcroForm structure and signature-specific catalog state.

## Product boundary

This tool intentionally creates a new PDF that is no longer digitally signed. It does not validate signer identity or certificate trust; that remains the job of **Verify Signature**. It does not decrypt password-protected PDFs without valid credentials and is not intended to bypass PDF access permissions.

## Deferred / known boundaries

- Remove Images still targets Image XObjects. Inline content-stream images (`BI … ID … EI`) remain an explicit boundary because robust support would require a content-stream parser/dependency expansion rather than a small qpdf JSON mutation.
- Multi-party/remote signing, cloud connectors, AI summarization and translation remain provider/credential/product decisions rather than self-contained engine gaps.

## V1.3 acceptance rule

A new V1.3 capability is accepted only when its production route/UI is wired, real regression coverage passes on the exact branch HEAD, and no weaker fallback silently changes the documented semantics.
