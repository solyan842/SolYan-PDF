# SolYan PDF V1.3 Parity Audit

## Scope

V1.3 continues the OSS-first parity policy after the self-contained V1.2 release. New work must close a concrete capability gap, prefer an existing SolYan engine or maintained upstream before adding dependencies, and keep provider/credential-dependent product families outside the self-contained core unless a product decision explicitly brings them in.

## Completed

### Remove Digital Signatures

Status: **implemented and regression-gated**.

SolYan PDF now provides `POST /pdf/remove-signatures` and a frontend tool at `/remove-signatures`.

The implementation uses the existing qpdf JSON structural pipeline rather than introducing a new PDF engine. It:

- walks AcroForm field trees, including inherited `/FT` values, and removes `/Sig` fields;
- removes signature Widget annotations from page `/Annots` while preserving non-signature form fields;
- removes the indirect signature `/V` payload references and rewrites the PDF so orphan signature/certificate objects are not retained as reachable document state;
- removes signature-related catalog permission references (`/DocMDP`, `/UR`, `/UR3`) and `/DSS` when present;
- preserves ordinary AcroForm fields;
- returns an unsigned input byte-for-byte when no signature-related state is found;
- validates rewritten output with `qpdf --check`.

The dedicated CI gate creates a real PKCS#12 fixture, signs the PDF through SolYan's existing pyHanko service, verifies one cryptographically valid embedded signature before processing, removes it through the production API, checks that a normal text field survives, checks that signature markers are absent from expanded PDF structure, and verifies through pyHanko that the result contains zero embedded signatures.

#### OSS reference

Stirling-PDF was reviewed as the maintained parity reference for this capability. Its current PDFBox path flattens top-level signature fields. SolYan keeps the same user-level capability while using the repository's existing qpdf/pyHanko stack and explicitly covers nested AcroForm structure and signature-specific catalog state.

#### Product boundary

This tool intentionally creates a new PDF that is no longer digitally signed. It does not validate signer identity or certificate trust; that remains the job of **Verify Signature**. It does not decrypt password-protected PDFs without valid credentials and is not intended to bypass PDF access permissions.

### PDF Inspector / Get ALL Info

Status: **implemented and regression-gated**.

Stirling-PDF's maintained `get-info-on-pdf` capability was reviewed as the parity reference. SolYan closes the same product gap without adding a new PDF engine: the backend image already contains qpdf and Poppler utilities.

SolYan's `POST /pdf/info` and `/pdf-info` UI combine:

- Poppler `pdfinfo` for user-facing document and metadata fields;
- `pdffonts` and `pdfimages -list` for bounded font/image inventories;
- qpdf JSON traversal from the catalog root for reachable structural counts, including pages, streams, object types, Image/Form XObjects, AcroForm fields, signature fields, embedded files, optional-content groups, outlines, XFA, actions and active annotations;
- qpdf encryption inspection for encryption state and permission summaries;
- SHA-256 and byte size for input identity;
- password support for encrypted PDFs, with invalid credentials rejected rather than silently returning a partial report.

Safety and boundedness rules:

- 100 MB upload ceiling shared with the backend PDF surface;
- at most 100,000 reachable qpdf objects are traversed;
- font/image table output is capped at 500 rows per category and reports truncation;
- PDF-origin metadata is returned as data and rendered through ordinary React text nodes; the UI does not use `innerHTML` or `dangerouslySetInnerHTML`;
- the inspector is read-only and does not claim malware detection or complete semantic validation.

The dedicated gate generates a real PDF containing a font, raster Image XObject, ordinary AcroForm field, signature field, embedded attachment, JavaScript OpenAction and deliberately HTML-shaped metadata. It checks qpdf/Poppler output, production API aggregation, exact metadata preservation through the JSON API, safe frontend wiring, encrypted-PDF inspection with the correct password, invalid-password rejection, and always uploads diagnostic logs. Backend CI, Frontend CI and the dedicated PDF Info Inspector CI all passed on the accepted feature implementation before this audit status was promoted.

### Unlock PDF Forms

Status: **implemented and regression-gated**.

Stirling-PDF's maintained `unlock-pdf-forms` controller was reviewed as the parity reference. Its behavior clears the PDF field ReadOnly bit, removes field `/Lock` entries, sets AcroForm appearances as needed and best-effort rewrites XFA `access="readOnly"` to `access="open"`.

SolYan uses the existing qpdf JSON engine rather than adding PDFBox or another PDF library. The implementation:

- traverses bounded AcroForm `/Fields` and `/Kids`, rejects cycles and limits depth/node count;
- clears only bit 1 (ReadOnly) from `/Ff`, preserving every other field flag and the existing field value;
- removes `/Lock` entries without flattening or deleting fields;
- keeps already-writable/no-form PDFs byte-identical;
- discovers only XFA streams referenced by the AcroForm, exports those streams individually with generalized decoding and rewrites `access="readOnly"` to `access="open"`;
- caps XFA at 256 referenced streams and 10 MB decoded per stream rather than decoding every content stream in the document;
- sets `/NeedAppearances` only when an actual form/XFA change occurs;
- validates rewritten output with `qpdf --check`.

The dedicated gate includes a field with ReadOnly plus an unrelated multiline flag, preserved field values, a `/Lock` dictionary, a Flate-compressed XFA packet containing multiple read-only attributes, a byte-identical writable no-op fixture, field-tree cycle rejection and qpdf validity. The UI explicitly separates this capability from password decryption: encrypted PDFs must first be decrypted with a valid password using the existing Unlock PDF tool. Backend CI, Frontend CI and the dedicated Unlock PDF Forms CI all passed on the accepted feature implementation before this audit status was promoted.

### Split Scanned Photos

Status: **implemented and regression-gated**.

Stirling-PDF's maintained `extract-image-scans` controller and `split_photos.py` were reviewed as the parity reference. SolYan reuses the OCR service's already-pinned OpenCV 4.10 and PDFium 5.14 stack, so this capability adds no runtime dependency.

SolYan's `/ocr/scanner-photo-split` pipeline:

- accepts the OCR service's existing bounded PDF/image formats and 50 MB upload ceiling;
- renders PDF pages temporarily at up to 300 DPI with PDFium, capped to a 4,200 px long edge, 100 pages and 400 million aggregate raster pixels;
- estimates scanner-bed color from edge samples only instead of sampling the page center, avoiding a centered photograph biasing the background estimate;
- computes color distance in signed integer space, avoiding `uint8` wraparound around 0/255 while applying the tolerance threshold;
- detects external foreground contours, filters by bounding-box area plus contour area, and sorts regions deterministically top-to-bottom then left-to-right rather than exposing OpenCV contour enumeration order;
- optionally expands each crop by a bounded border and deskews crops whose dominant rectangle exceeds the configured angle threshold;
- encodes each result immediately as PNG, caps output at 500 photos / 250 MB encoded bytes, and returns one deterministic ZIP with `page-XXX-photo-XXX.png` names;
- rejects a scan with no detected photo regions instead of returning an empty archive.

The dedicated regression gate creates a synthetic scanner image with two axis-aligned photos and one 12-degree rotated photo. It requires three stable regions, verifies the scanner-bed color estimate, proves the rotated crop is deskewed back to within 1.5 degrees, exercises the production FastAPI route for both image and two-page PDF input, checks deterministic ZIP names and photo/page counts, and requires a blank scan to return HTTP 422. Backend proxy parameter validation and UI/dependency wiring are gated separately. The dedicated Scanner Photo Split CI, Backend CI, Frontend CI and OCR Service CI all passed on the accepted feature implementation before this audit status was promoted.

### PDF to HTML

Status: **implemented and regression-gated**.

Stirling-PDF's maintained PDF-to-HTML capability was reviewed as the parity reference. Both products use Poppler `pdftohtml`; SolYan already ships `poppler-utils` in the backend image, so this capability adds no runtime dependency.

SolYan's `POST /pdf/to-html` and `/pdf-to-html` UI:

- generate a single self-contained HTML file with `pdftohtml -s -noframes -dataurls`, keeping raster images inline as data URLs instead of requiring sidecar files;
- accept an optional first/last page range and optional user/owner password, rejecting an invalid password with HTTP 401;
- reuse the backend's existing 100 MB PDF upload ceiling and cap generated HTML at 150 MB;
- preserve ordinary HTTP/HTTPS-style links while neutralizing downloaded HTML links whose `href` uses `javascript:`, `vbscript:`, `file:` or `data:` schemes;
- inject a restrictive Content Security Policy that blocks scripts, objects, forms, external network loads and base-URL rewriting while allowing embedded images and inline layout CSS;
- expose the number of neutralized dangerous links through `X-SolYan-Blocked-HTML-Links`;
- explicitly treat the result as a display/layout conversion rather than an interactive preservation of PDF forms, annotations or JavaScript.

The dedicated regression gate builds a real two-page fixture with text, a raster Image XObject and a deliberately dangerous `javascript:` URI annotation. It verifies self-contained image embedding, page-range selection, dangerous-link neutralization, CSP injection, encrypted-PDF conversion with the correct password, invalid-password rejection and route/UI/dependency wiring, then uploads HTML/PDF/log evidence. The first encrypted-password run exposed that Poppler's quiet mode suppressed the diagnostic needed to distinguish an invalid password; the accepted implementation removed that suppression, retained Poppler stderr, and the dedicated PDF to HTML CI, Backend CI and Frontend CI all passed on the corrected feature implementation before this audit status was promoted.

### PDF to Text

Status: **implemented and regression-gated**.

Stirling-PDF's maintained PDF-to-Text conversion was reviewed as the parity reference. SolYan reuses Poppler `pdftotext`, already provided by the backend image's `poppler-utils`, so this capability adds no runtime dependency.

SolYan's `POST /pdf/to-text` and `/pdf-to-text` UI:

- export the existing PDF text layer as UTF-8 plain text without OCR or an external service;
- support optional first/last page selection up to page 10,000;
- expose Poppler's layout-preserving mode for simple columns/tables and optional form-feed page separators;
- accept a valid user or owner password for encrypted PDFs and reject invalid credentials with HTTP 401;
- reuse the backend's 100 MB PDF upload ceiling, bound conversion time to 180 seconds and cap generated TXT output at 50 MB;
- explicitly direct image-only scan users to the OCR tool rather than silently rasterizing or inventing text.

The dedicated regression gate generates a real two-page PDF with positioned Type1 text. It verifies default UTF-8 extraction, form-feed page breaks, exact page-range filtering, layout mode, page-break suppression, invalid-range rejection, encrypted-PDF extraction with the correct password, invalid-password rejection and production route/UI/dependency wiring, then uploads the source PDFs, text outputs and diagnostic log as CI evidence. The dedicated PDF to Text CI, Backend CI and Frontend CI all passed on the accepted feature implementation before this audit status was promoted.

### PDF to CBZ

Status: **implemented and regression-gated**.

Stirling-PDF's maintained `PdfToCbzUtils` path was reviewed as the parity reference. SolYan reuses Poppler utilities already present in the backend image rather than adding a comic/ebook engine.

SolYan's `POST /pdf/to-cbz` and `/pdf-to-cbz` UI:

- use Poppler `pdfinfo` and `pdftoppm` to render selected PDF pages as PNG;
- package pages into deterministic `page_###.png` CBZ entries with numeric ordering that remains correct beyond page 9;
- support 72–300 DPI, optional page ranges and valid PDF passwords;
- bound input to 100 MB, output to 500 MB, rendered output to at most 1,000 pages and accepted page indices to 10,000;
- explicitly document that CBZ is a rasterized reading format and does not preserve selectable text, forms, annotations or other interactive PDF structures.

The dedicated gate creates a real 12-page PDF, checks deterministic archive order and rendered page count, exercises DPI/page-range behavior, validates encrypted-PDF conversion with the correct password and rejection of invalid credentials, and verifies production route/UI wiring. The accepted implementation passed the dedicated PDF to CBZ regression before merge.

### PDF to Markdown

Status: **implemented and regression-gated**.

Stirling-PDF's maintained Markdown extraction was reviewed as the parity reference. SolYan deliberately avoids adding a second Markdown parser: it routes PDF input through the already-shipped PP-StructureV3 structured-layout pipeline and reuses that engine's `save_to_markdown()` output.

SolYan's `POST /pdf/to-markdown` and `/pdf-to-markdown` UI:

- are a thin backend adapter over the production `/ocr/structured` pipeline;
- use PP-StructureV3 layout/OCR semantics for both scanned and structured PDFs;
- keep the OCR service's existing 50 MB input bound;
- return UTF-8 `text/markdown` plus engine/page headers;
- explicitly document that the Markdown is a semantic/layout extraction and not a byte-perfect representation of PDF geometry or interactive content.

The dedicated gate exercises the production PP-StructureV3 Markdown assembly path and the public backend adapter, including engine/page propagation and UI wiring. The accepted implementation passed the dedicated PDF to Markdown regression before merge.

### PDF to XML

Status: **implemented and regression-gated**.

SolYan uses Poppler `pdftohtml -xml` because the engine is already shipped and provides explicit `pdf2xml` page/font/text geometry. The maintained Stirling-PDF XML surface was used as the parity reference, but no extra LibreOffice routing was needed for this gap.

SolYan's `POST /pdf/to-xml` and `/pdf-to-xml` UI:

- return one UTF-8 `pdf2xml` document containing positioned text, font information and page geometry;
- support optional page ranges up to page 10,000, precise coordinates, hidden text and valid user/owner passwords;
- omit raster sidecars so the output remains one XML document;
- bound input to 100 MB, XML output to 100 MB and conversion time to 180 seconds;
- reject unexpected entity declarations before parsing/returning the XML rather than exposing an unbounded XML entity surface.

The feature was first validated on a stale pre-CBZ/Markdown branch, then explicitly refreshed onto current `main` and its real regression gate rerun on the refreshed exact HEAD. The stale superseded PR was closed rather than force-updated. The accepted implementation passed the dedicated PDF to XML regression before merge.

### PDF to RTF

Status: **implemented and regression-gated**.

Stirling-PDF's maintained LibreOffice PDF-import path was reviewed as the parity reference. SolYan extends the already-bundled Office service instead of adding another converter.

SolYan's `POST /pdf/to-rtf` and `/pdf-to-rtf` UI:

- extend the Office service PDF-import target set with `rtf`;
- use LibreOffice `writer_pdf_import`, then export `rtf:Rich Text Format`;
- validate RTF magic in both the Office service and public backend adapter;
- reuse the Office/PDF proxy's existing 100 MB bound;
- explicitly document that PDF import may not preserve every layout/editability detail.

The first CI version used RTF→TXT as its content oracle and exposed a LibreOffice behavior: text retained inside later RTF `SHAPE` records can disappear from the subsequent TXT export even though the RTF itself contains the text. The accepted gate therefore validates the required source strings directly in the RTF payload, then uses LibreOffice RTF→TXT only as a reopen/readability smoke test. Backend, Frontend, Office-service compatibility and the corrected dedicated PDF to RTF gate passed before merge.

### PDF to CSV

Status: **implemented and regression-gated**.

Stirling-PDF's maintained CSV extraction was reviewed as the parity reference. Instead of adding Tabula/Camelot or another table engine, SolYan reuses its existing production PP-StructureV3 `/ocr/xlsx` pipeline, then performs a bounded XLSX→CSV adaptation with the Python standard library.

SolYan's `POST /pdf/to-csv` and `/pdf-to-csv` UI:

- send the source PDF through the existing PP-StructureV3 table/XLSX path;
- convert meaningful worksheets to quote-all CSV with UTF-8 BOM and CRLF records for spreadsheet compatibility;
- preserve numeric values, including negative numbers, while neutralizing textual cells beginning with `=`, `+`, `-` or `@` to reduce CSV formula-injection risk;
- omit empty/raster-only fallback worksheets;
- return one CSV when there is one useful worksheet and a deterministic ZIP when there are multiple useful worksheets;
- keep multiple detected tables from one source page stacked in that page's worksheet/CSV, matching the existing XLSX pipeline rather than inventing a second table-fragment model;
- bound PDF input to 50 MB, compressed XLSX to 250 MB, expanded XLSX parts to 500 MB, CSV/archive output to 250 MB, worksheets to 1,000 and cells to 2,000,000 per worksheet;
- normalize worksheet relationship paths and reject paths escaping the XLSX `xl/` tree.

The dedicated deterministic OOXML gate covers Vietnamese Unicode, UTF-8 BOM, negative numeric cells, formula-like string neutralization, empty-sheet skipping, single-CSV and multi-CSV ZIP behavior, upstream HTTP error propagation and non-PDF rejection. The initial CI failures were test/infrastructure defects rather than product failures: the first omitted hash-locked transitive backend dependencies, and the second used a whitespace-sensitive XML string replacement to build the single-sheet fixture. Both were corrected without weakening conversion semantics. On the accepted exact branch HEAD, PDF to CSV CI, Backend CI and Frontend CI all passed before merge.

## Deferred / known boundaries

- Remove Images still targets Image XObjects. Inline content-stream images (`BI … ID … EI`) remain an explicit boundary because robust support would require a content-stream parser/dependency expansion rather than a small qpdf JSON mutation.
- PDF → EPUB/AZW3 remains deferred from the self-contained converter queue because the maintained reference implementation uses Calibre; adding that path would be a deliberate runtime/dependency expansion rather than reuse of an already-shipped SolYan engine.
- PDF → CBR remains lower priority than CBZ because RAR creation introduces additional tooling/licensing/deployment complexity while CBZ already covers the open ZIP-based comic archive path.
- Multi-party/remote signing, cloud connectors, AI summarization and translation remain provider/credential/product decisions rather than self-contained engine gaps.

## V1.3 acceptance rule

A new V1.3 capability is accepted only when its production route/UI is wired, real regression coverage passes on the exact branch HEAD, and no weaker fallback silently changes the documented semantics.
