# SolYan PDF V1.4 Parity Audit

Status: **self-contained scope complete**.

V1.4 continues the maintained-OSS, self-contained parity pass after V1.3/v0.1.6. The rule remains: reuse already-shipped browser/server engines first; do not add a new runtime, cloud provider or credential requirement merely to increase tool count.

## Research checkpoint

The Vietnamese utility set was rechecked against the current Bambu utility surface before starting V1.4. Bambu still exposes the same 13 utility families already implemented by SolYan PDF, so there is no missing Vietnamese-utility parity item to duplicate in this lane.

Provider-dependent families remain outside the automatic self-contained queue: multi-party remote signing, cloud-storage connectors, AI summarization and translation still require explicit product/provider decisions.

The maintained Stirling-PDF surface was also rechecked while closing V1.4. SolYan deliberately did not add features merely to increase parity count. In particular, Calibre-backed EPUB/AZW3, Ghostscript/GhostPDL-backed PCL/XPS and provider-backed product families remain explicit dependency/product decisions rather than release blockers.

## Auto Redact Text

Status: **implemented, security-gated and merged** in PR #104.

Maintained open-source PDF platforms expose automatic text redaction as a useful gap beyond SolYan's existing manual secure redaction. SolYan implements this without adding another PDF engine:

- PDF.js reads the existing text layer locally in the browser;
- each non-empty input line is a literal search term, with optional case sensitivity;
- matching is intentionally conservative: the whole PDF text-run containing a term is covered instead of estimating substring glyph bounds and risking partial disclosure;
- only pages containing matches are rendered at 150 DPI;
- matched text-run rectangles are painted black on the trusted raster;
- the affected pages are rebuilt from those rasters with `pdf-lib` and their original content streams are not copied into the output;
- untouched pages are copied from the source PDF;
- the manual Editor redaction API remains backwards-compatible while the secure helper now supports multiple rasterized page replacements.

### Explicit product boundaries

- Auto Redact searches the **existing PDF text layer**. A scan with no text layer must be OCRed first; there is no silent OCR fallback.
- Matching is per PDF.js text-run. A phrase split across multiple runs may need to be entered as shorter pieces.
- Whole-run coverage can redact more text than the exact substring; this is deliberate to favor non-disclosure over visually tight matching.
- Affected pages become raster pages. Selectable/vector text, forms, annotations and other interactive source content on those pages are not preserved as interactive objects.
- Untouched pages remain copied pages, but document-level structures are not newly guaranteed by the security-first page-tree rebuild beyond the existing secure-redaction boundary.

### Hard bounds

- PDF input: 100 MB
- source pages: 500
- terms: 20
- term length: 200 characters
- matched text-runs: 500
- affected pages: 40
- raster pixels per affected page: 25,000,000
- aggregate affected-page raster pixels: 80,000,000

### Accepted regression evidence

The dedicated `Auto Redact Text CI` gate on exact PR #104 HEAD verifies:

- literal PDF.js matching and case-sensitivity behavior;
- secure multi-page raster replacement and duplicate-page rejection;
- valid output through `qpdf --check` with unchanged page count;
- text on an untouched page remains extractable;
- the redacted secret is absent from `pdftotext` output;
- the redacted secret is absent from expanded QDF serialized reachable content;
- production wiring and all documented bounds remain present;
- the production Next.js frontend builds successfully.

The existing `Secure Redaction CI` also remains green after generalizing the helper, proving the manual Editor redaction path did not regress. All pull-request-triggered regression workflows on the accepted exact HEAD completed successfully before merge.

## Scanner Effect

Status: **implemented, regression-gated and merged** in PR #106.

The maintained Stirling-PDF Scanner Effect surface was reviewed as the parity reference. SolYan reuses its existing browser raster stack instead of adding PDFBox/ImageMagick or another application runtime:

- PDF.js renders each page locally;
- Canvas applies brightness, contrast, deterministic noise, optional paper yellowing, blur, paper border and page skew;
- `pdf-lib` rebuilds the processed page images into a PDF while preserving the source physical page dimensions;
- output supports grayscale or color;
- quality presets track the maintained upstream behavior surface: High at 150 DPI, Medium at 100 DPI and Low at 75 DPI, with progressively stronger blur/noise/contrast treatment;
- skew presets are None, Slight (±2°), Moderate (±5°) and Severe (±8°);
- unlike upstream random scan variation, SolYan seeds angle and noise by page so identical input/settings are reproducible and CI-testable.

### Explicit product boundaries

- Scanner Effect is intentionally **rasterized**. Selectable/vector text, forms and annotations are not retained as interactive source content in the result.
- It is a visual simulation only: it is not OCR, does not prove that a document came from a physical scanner, and must not be represented as document provenance/authenticity evidence.
- The simulated border/rotation can slightly shrink the visible source image inside the original physical page rectangle so the full rotated raster remains visible.
- The effect is deterministic by design rather than physically random; this favors reproducibility over trying to imitate every stochastic scanner artifact.

### Hard bounds

- PDF input: 100 MB
- source pages: 100
- source raster pixels per page: 25,000,000
- effect-canvas pixels after border/rotation: 32,000,000
- aggregate source raster pixels: 150,000,000
- paper border: 0–80 pixels

### Accepted regression evidence

The dedicated `Scanner Effect CI` gate on exact PR #106 HEAD verifies:

- the High/Medium/Low preset values and rotation-variance map;
- deterministic page seed, deterministic skew and deterministic seeded noise;
- exact grayscale and color brightness/contrast pixel semantics;
- yellowed-paper color shift and alpha preservation;
- production raster bounds, dashboard wiring and explicit anti-provenance/rasterization warnings;
- the production Next.js frontend builds successfully.

All pull-request-triggered regression workflows associated with the accepted exact HEAD completed successfully before merge, including Frontend, Color Transform, Auto Redact, Auto Rotate, Remove Images and Remove Blank Pages gates.

## PDF → PostScript / EPS

Status: **implemented, regression-gated and merged** in PR #108.

The maintained Stirling-PDF vector-export surface was reviewed as the parity reference. Stirling uses Ghostscript devices for EPS/PS/PCL/XPS. SolYan limits the self-contained implementation to the formats already supported directly by its existing Poppler runtime:

- `POST /pdf/to-postscript` uses Poppler `pdftops` already provided by `poppler-utils` in the backend image;
- PS supports multi-page output and preserves original page sizes via `-origpagesizes`;
- EPS is explicitly single-page and requires one selected page;
- PostScript Level 2 and Level 3 are supported, with Level 3 as the default;
- optional first/last page selection is supported for PS;
- encrypted PDFs may use a supplied user or owner password;
- output is checked for a PostScript header, with explicit EPSF validation for EPS.

### Explicit product boundaries

- PostScript is an executable page-description language for an interpreter. SolYan only generates PS/EPS from PDF; it does not accept or execute uploaded PostScript in this feature.
- Users should open generated PS/EPS only in trusted/sandboxed interpreters or applications appropriate to their environment.
- PCL and XPS remain deferred because the maintained reference implementation requires Ghostscript/GhostPDL device support not currently shipped by the SolYan backend.
- This converter preserves a vector page-description representation but does not promise byte-identical PDF semantics, forms, annotations, JavaScript or other PDF-only interactive structures.

### Hard bounds

- PDF input: 100 MB
- generated PS/EPS: 250 MB
- page index: 1–10,000
- converter timeout: 180 seconds

### Accepted regression evidence

The dedicated `PDF to PostScript CI` gate on exact PR #108 HEAD verifies:

- a real two-page PDF converts to multi-page Level 3 PS;
- a selected page converts to single-page Level 2 PS;
- a selected page converts to EPS with EPSF and BoundingBox headers;
- invalid EPS multi-page ranges, reversed ranges, unsupported formats and non-PDF input are rejected;
- production route/CORS/dashboard wiring and hard bounds remain present;
- the production Next.js frontend builds successfully.

Before merge, every pull-request-triggered workflow associated with the exact accepted PR #108 HEAD completed successfully, including Backend CI, Frontend CI, Auto Redact, Color Transform and all other triggered regression gates. PR #108 merged into `main` as `824804b95b6491d15e3fe9580e0ee1fe1caed8b8`.

## Deferred by design

These items are not unfinished work in the V1.4 self-contained scope:

- PDF → EPUB/AZW3: maintained implementations rely on Calibre, which is a deliberate runtime expansion;
- PDF → PCL/XPS: maintained vector export relies on Ghostscript/GhostPDL devices not currently shipped by SolYan;
- PDF → CBR: RAR creation adds deployment/licensing/tooling complexity while CBZ is already supported;
- inline `BI … ID … EI` image removal: robust support needs a real content-stream parser/dependency expansion;
- multi-party remote signing, cloud-storage connectors, AI summarization and PDF translation: separate provider/product/credential decisions.

No additional V1.4 feature should be added merely to increase the tool count. Future work must identify a concrete user-value gap and pass the repository OSS-first/speed gate first.

## V1.4 acceptance rule

A V1.4 feature is accepted only when its production route/UI is wired, its security or fidelity semantics are stated explicitly, real regression coverage passes on the exact branch HEAD, and the change does not silently widen dependency/provider scope.
