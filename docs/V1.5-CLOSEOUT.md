## V1.5 accepted capability summary

### Vector, signing and container semantics

- **PDF → SVG** — vector-first Poppler/Cairo export through the already-shipped `pdftocairo` engine.
- **PDF certification / DocMDP** — extends the existing pyHanko PKCS#12 signing path instead of adding a second signing stack.
- **PDF Portfolio / Collection** — reuses qpdf attachment handling plus catalog Collection markers.
- **PDF Page Labels** — reuses qpdf page-label support for logical labels without painting page content.

### Secure redaction improvements

- **Safe Regex Auto Redact** — bounded opt-in regex subset and controlled presets on the existing PDF.js matcher.
- **Unicode Whole Word Auto Redact** — Unicode Letter/Number/Mark/underscore boundaries plus NFC normalization for literal matching.
- The security-first output model remains unchanged: affected pages are raster-rebuilt rather than retaining their original affected-page content streams.

### Flatten, numbering and metadata

- **Full Page Flatten** — adds browser-local full-page raster flatten while preserving the existing qpdf forms/annotations mode as the non-raster default path.
- **Advanced Page Numbers / Bates** — 9 positions, CropBox-relative margins, templates, start number, zero-padding, standard fonts, size and color.
- **Advanced Metadata** — CreationDate/ModDate, Trapped, bounded custom Info fields and an explicit Delete All path that also removes catalog `/Metadata` and `/PieceInfo`.

### Image conversion parity

- **Advanced PDF → Images** — selected pages, explicit DPI, PNG/JPEG/WebP, Color/Greyscale/B&W, annotation render toggle, ZIP or one vertical composite image.
- **Advanced Images → PDF** — preserves image-sized pages as the default and adds A4 Fit/Fill, A4 auto-rotate and Color/Greyscale/B&W.

## Audited tools retained without another implementation lane

The following were inspected and intentionally kept as-is because the current SolYan implementation already covered the useful self-contained product shape or the missing control would require a different engine rather than a truthful option on the existing one:

- Watermark / Stamp;
- Bookmark / Outline editor;
- Crop PDF;
- Resize / Scale pages;
- Color Transform;
- Compress Images.

The exact rationale for each is recorded in `docs/V1.5-PARITY-STATUS.md` so the audit is not repeated in a later session.

## OSS-first architecture result

The accepted V1.5 scope reuses runtime families already present in SolYan PDF:

- qpdf;
- Poppler/Cairo;
- pyHanko;
- PDF.js;
- Canvas;
- pdf-lib;
- JSZip.

No new application runtime, cloud provider, hosted key-custody system, AI provider or codec family is introduced by the accepted self-contained V1.5 scope.

## Deferred by design

The following are **not unfinished V1.5 implementation work**. They require separate product/provider/credential or materially different privacy decisions:

- multi-party or remote signing workflows and hosted key custody;
- cloud-storage connectors;
- AI summarization or broader LLM document intelligence;
- PDF/document translation;
- other provider-backed features that require new credentials or remote data handling.

These items must not be pulled into V1.5 implicitly just because the self-contained parity pass is complete.

## Verification evidence boundary

Each implementation lane was merged only after its applicable exact-head CI completed successfully. Relevant evidence included Frontend/Backend/Signature/feature-specific regressions depending on the files touched. When an Auto Redact run failed during V1.5, the raw failed job log was read first, the concrete TypeScript error was fixed, and a new exact-head run was required before merge.

The permanent PDF → Office V1 release policy remains unchanged at **27 cases / 68 source pages**; no threshold, corpus or editability/fidelity requirement was weakened by V1.5.

The docs-only parity checkpoint PR #123 intentionally triggered no workflow because current path filters do not run product CI for that file-only change. Its parent product state had already passed the applicable feature gates before merge.

## Release readiness meaning

V1.5 can proceed to release packaging only after all of the following are satisfied:

1. this close-out record is merged into current `main`;
2. repository-wide Actions state is refreshed and all relevant current release gates are verified;
3. release version metadata is synchronized to the next patch version across package, lockfile, backend and release documents;
4. release notes, changelog and dependency manifest identify the exact V1.5 scope and boundaries;
5. no temporary prepare/diagnostic workflow or script remains in the release tree;
6. the release tag and GitHub Release target the exact intended `main` commit;
7. the created release is re-fetched and verified non-draft/non-prerelease unless explicitly intended otherwise.

After this close-out, new feature work belongs to a later lane and must begin with a concrete user-value gap plus the repository OSS-first/speed gate rather than reopening V1.5 by default.
