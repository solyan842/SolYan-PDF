# SolYan PDF V1.5 — Safe Regex Auto Redact

Status: **ACCEPTED / SELF-CONTAINED V1.5 LANE**

## User-value gap

SolYan already performs secure local Auto Redact by matching literal text in the PDF.js text layer, blacking the entire matching text-run, rasterizing only affected pages, and rebuilding those pages without their original content streams. The missing capability is bounded pattern matching for recurring sensitive-data shapes such as email addresses, payment-card numbers, phone numbers and account identifiers.

Current Stirling-PDF redaction exposes regex search as a product capability. SolYan does not copy its backend implementation: this lane keeps SolYan's existing browser-local PDF.js matching and secure raster-redaction pipeline.

## OSS-first / dependency decision

No new regex runtime, WASM module, backend service or npm dependency is added.

JavaScript's built-in `RegExp` is reused only behind a deliberately restricted **Safe Regex** compiler. Arbitrary JavaScript regular expressions are not accepted because user-supplied catastrophic-backtracking patterns could block the browser main thread. The existing literal mode remains the default and retains its previous API/behavior.

## Safe Regex boundary

Custom patterns are intentionally a subset rather than full JavaScript regex syntax.

Per custom pattern:

- maximum 200 characters;
- no groups or parentheses, therefore no lookahead/lookbehind;
- no numeric, named or subroutine backreferences;
- no zero-width `\b` / `\B` word-boundary escape;
- no unbounded `*` or `+` quantifiers;
- no open-ended `{m,}` quantifier;
- bounded `{m}` and `{m,n}` are allowed only with `0 <= m <= n <= 64`;
- `?` is allowed, subject to the complexity budget;
- at most 16 top-level alternation branches;
- optional/range branching is bounded by a complexity budget of 4096;
- a compiled pattern that can match the empty string is rejected before the PDF is loaded;
- regex mode refuses any individual PDF.js text-run longer than 4096 characters.

This is a product safety boundary, not a claim that the subset implements every regular-expression construct. Unsupported patterns fail explicitly instead of falling back to unrestricted regex execution.

## Controlled presets

SolYan exposes five internally defined presets whose pattern shapes are reviewed separately from the custom-pattern grammar:

- `<EMAIL>` — conventional email-like address;
- `<CARD>` — 16 digits with optional spaces/hyphens between four-digit groups;
- `<SSN>` — U.S.-style `NNN-NN-NNNN` shape;
- `<VN_PHONE>` — common `0...` or `+84...` Vietnamese phone-number shape;
- `<IBAN>` — uppercase IBAN-like alphanumeric shape.

Presets are convenience matchers, not semantic validation or proof that a matched value is a real account/card/phone identifier.

## Matching and redaction semantics

Safe Regex changes only the **match predicate**. The secure redaction model is unchanged:

1. PDF.js reads each page's text layer locally in the browser.
2. A literal term or compiled Safe Regex is evaluated against each individual PDF.js text-run.
3. If any configured matcher hits, SolYan redacts the bounding rectangle of that entire text-run.
4. Only pages with matches are rasterized at 150 DPI.
5. Those pages are rebuilt from the raster output; their original text/vector/form/annotation content streams are not copied into the replacement page.
6. Unaffected pages are copied through the existing secure-redaction rebuild path.

Patterns do **not** match across PDF.js text-run boundaries. As a result, a visually continuous value split by the source PDF into multiple text items may require shorter patterns or preprocessing/OCR.

## Resource gates

Existing Auto Redact limits remain, with an additional text-run bound for pattern mode:

- 100 MB input PDF;
- 500 pages;
- 100,000 non-empty PDF.js text-runs per operation;
- 20 literal terms / Safe Regex entries;
- 200 characters per entry;
- 500 matching text-runs;
- 40 pages requiring redaction;
- 25 million raster pixels per redacted page;
- 80 million raster pixels across the operation;
- 4096 characters maximum for an individual text-run evaluated by Safe Regex.

## Security/fidelity boundary

The tool deliberately blacks the full matching text-run, so the visible redaction can be wider than the exact substring that matched. This is preferred over pretending to provide character-perfect geometry when PDF.js exposes text in source-dependent runs.

Rasterizing a matched page removes editable/searchable text, vector fidelity, forms and interactive annotations from that page. This is the existing secure-redaction trade-off and remains explicit in the UI.

PDF scans without a text layer are not pattern-matched directly; users must OCR first.

## Acceptance gate

The existing `Auto Redact Text CI` remains the regression gate for:

- direct TypeScript compilation of the Auto Redact helpers;
- existing literal matching semantics;
- multi-page secure raster rebuild;
- `qpdf --check` validity;
- proof that redacted source text is not extractable/reachable in the rebuilt PDF while untouched-page text remains;
- production Auto Redact wiring and bounded resource constants;
- full Next.js production build.

The current connector session is blocked from modifying `.github/workflows/*`, so a dedicated Safe Regex assertion cannot be added to that workflow here. That restriction is not bypassed through lower-level Git plumbing. The Safe Regex compiler therefore also performs its safety rejection synchronously before PDF processing, and the production build remains mandatory for this lane.
