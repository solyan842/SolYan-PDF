# SolYan PDF V1.7 — Cloud Storage Connectors

Status: architecture lock before implementation.

## Goal

Add cloud storage as an optional I/O layer around the existing PDF tools without coupling storage providers to PDF processing engines.

V1.7 starts with Google Drive and Microsoft OneDrive. S3-compatible storage and WebDAV remain follow-on adapters behind the same provider contract.

## Architecture

SolYan core keeps a narrow `StorageProvider` contract:

- provider capability/status discovery;
- OAuth authorization start/callback/logout;
- list/browse provider-visible files;
- download a selected PDF through the SolYan backend;
- upload a new PDF;
- replace an existing PDF only when the user explicitly requests overwrite.

Provider credentials are deployment configuration only. Client secrets and refresh tokens must never be returned to browser code or stored in `localStorage`.

The current single-worker backend keeps short-lived OAuth state and user token sessions in a bounded in-memory vault keyed by a random HttpOnly session cookie. This is intentionally restart-ephemeral. A future multi-replica deployment must replace this vault with a shared encrypted server-side session store; the provider contract must not change.

## Google Drive

Default OAuth scope: `https://www.googleapis.com/auth/drive.file`.

This is the least-privilege per-file Drive scope used by the V1.7 connector. In default mode the backend can list files the app is already allowed to access, download them, create new files and update app-authorized files. SolYan does not silently widen this to full-Drive access.

A Google Picker integration can later expose arbitrary user-selected Drive files while keeping the same `drive.file` permission model. Any short-lived access token exposed for Picker must stay in browser memory only; refresh tokens remain server-side.

## OneDrive

Use Microsoft identity platform OAuth authorization-code flow with PKCE and delegated Graph scopes:

- `Files.ReadWrite`
- `offline_access`

V1.7 uses Microsoft Graph v1.0 only. Uploads are routed through `createUploadSession` so interrupted/large uploads can resume without changing the public SolYan storage contract.

## Security boundaries

- Provider allow-list is server-side.
- OAuth `state` is random, single-use and expiring.
- PKCE is used for OAuth authorization-code flows.
- Redirect targets are constrained to the configured frontend origin; no open redirects.
- Access/refresh tokens are stored only in the backend session vault.
- OAuth/session responses use `Cache-Control: no-store`.
- File downloads/uploads are bounded by `CLOUD_STORAGE_MAX_FILE_SIZE`.
- V1.7 accepts PDF objects only and validates the `%PDF-` header before returning cloud downloads to PDF workflows.
- Provider error bodies are not reflected verbatim to the browser.
- Logout removes the server-side provider session immediately; provider revocation is a separate best-effort action.

## Operator configuration

Google Drive:

- `GOOGLE_DRIVE_CLIENT_ID`
- `GOOGLE_DRIVE_CLIENT_SECRET`
- optional `GOOGLE_PICKER_API_KEY`
- optional `GOOGLE_PICKER_APP_ID`

OneDrive:

- `ONEDRIVE_CLIENT_ID`
- `ONEDRIVE_CLIENT_SECRET`
- optional `ONEDRIVE_TENANT` (default `common`)

Shared:

- `CLOUD_STORAGE_CALLBACK_BASE_URL`
- `CLOUD_STORAGE_FRONTEND_BASE_URL`
- `CLOUD_STORAGE_SESSION_TTL_SECONDS`
- `CLOUD_STORAGE_MAX_FILE_SIZE`
- `CLOUD_STORAGE_COOKIE_SECURE`

No cloud credential is required for SolYan PDF to build, run ordinary PDF tools, or pass CI. A provider reports `configured=false` until its operator-owned OAuth application credentials are present.

## V1.7 acceptance scope

1. provider-neutral backend contract;
2. Google Drive OAuth + app-visible file list/download/upload/update with `drive.file`;
3. OneDrive OAuth + file list/download/upload/update via Graph v1.0;
4. frontend Cloud Storage workspace showing provider configuration/connection status and file operations;
5. deterministic mock-provider CI covering OAuth state/PKCE/session isolation, provider allow-list, bounded transfers and error sanitization;
6. no real provider credential in repository or CI.

Live OAuth with real Google/Microsoft accounts is a deployment diagnostic, not a release prerequisite, because it requires operator-owned OAuth applications and credentials.
