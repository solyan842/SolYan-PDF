# SolYan PDF V1.5 — OSS-first parity audit

Status: **ACTIVE / SELF-CONTAINED LANE**

V1.5 starts after the verified `v0.1.7` / V1.4 release. The lane keeps the repository rule that a feature must add clear user value and should reuse an already-shipped engine before adding another runtime, provider or dependency family.

## First accepted candidate — PDF → SVG

### User-value gap

SolYan already exports PDF to raster images, PostScript/EPS and several document/text formats, but did not expose a vector-friendly SVG export. SVG is useful for design, web assets, diagrams and downstream vector workflows where PNG/JPEG would throw away scalable geometry.

### OSS comparison

#### Poppler `pdftocairo` — selected

Poppler is already installed in the SolYan backend as `poppler-utils`. Its maintained `pdftocairo` CLI supports SVG output directly through `-svg`, page selection through `-f` / `-l`, user/owner passwords through `-upw` / `-opw`, and a resolution setting that controls rasterized regions when a vector construct cannot be represented natively.

Why selected:

- no new application runtime or container package family;
- already part of the deployed backend image and release dependency surface;
- supports encrypted PDFs using the same user/owner-password model as other Poppler converters;
- preserves vector representation where Cairo can express it;
- supports bounded raster fallback resolution for unsupported regions.

### MuPDF / `mutool` — rejected for this lane

Current MuPDF tooling also supports SVG vector output and has strong page/range controls. It is not currently shipped by SolYan, however, and upstream describes product embedding under AGPL unless a commercial license is obtained. Adding it solely for SVG would therefore expand both runtime and licensing surface without a demonstrated quality need over already-shipped Poppler.

### Stirling-PDF parity reference

The maintained Stirling-PDF PDF vector-export controller currently exposes EPS/PS/PCL/XPS through Ghostscript/GhostPDL paths. That is useful as a parity reference for vector-export product shape, but SVG is not part of that controller's current output set. SolYan therefore does not copy Stirling's runtime choice here; it uses the lighter engine already present in its own stack.

## Accepted SolYan behavior

Endpoint: `POST /pdf/to-svg`

- one selected page returns one `image/svg+xml` attachment;
- multiple selected pages return a ZIP containing one deterministic `page_NNN.svg` per physical source page;
- page range is optional; default is the whole document;
- encrypted PDFs accept a supplied password and try user-password then owner-password semantics;
- SVG XML is parsed after conversion and must have an SVG root element;
- `raster_dpi` is bounded to 72–300 DPI and only controls regions Poppler/Cairo must rasterize;
- input remains bounded by the shared 100 MB PDF limit;
- at most 100 SVG pages are emitted per request;
- each SVG is limited to 64 MB;
- aggregate raw SVG output is limited to 250 MB;
- the ZIP is independently limited to 250 MB;
- each Poppler page conversion is bounded by a 120-second command timeout.

### Important fidelity boundary

This is **vector-first**, not a promise that every PDF primitive stays vector. Poppler/Cairo can rasterize regions that cannot be represented natively in SVG; the selected raster DPI controls those fallback regions. Fonts/text may also be represented as paths/glyph definitions rather than editable semantic text depending on source content and Poppler behavior.

### Multi-page boundary

SVG itself is a single-canvas format. Real `pdftocairo -svg` behavior is treated as one SVG output per conversion target rather than a multi-page container, so SolYan intentionally invokes Poppler once per selected page and packages multi-page results into ZIP. This is an explicit product behavior, not an accidental CLI side effect.

### Security boundary

The endpoint converts **PDF → SVG only** and returns the generated SVG as a download attachment. SolYan does not accept or execute uploaded SVG in this path. SVG as a general web format can contain active/external content, so downstream embedding should still happen only in an appropriate trusted/sandboxed context; this feature does not claim to sanitize arbitrary third-party SVG files.

## Acceptance gate

The dedicated `PDF to SVG CI` must verify, through the public FastAPI route:

- a real two-page PDF becomes a ZIP with two valid SVG XML documents;
- a single selected page returns direct `image/svg+xml` with the source page dimensions;
- page-range ordering and out-of-range requests fail explicitly;
- DPI bounds are enforced;
- a 101-page request is rejected before conversion by the 100-page resource gate;
- encrypted input rejects a wrong password and accepts the correct user password;
- non-PDF input is rejected by the shared PDF input gate;
- production frontend wiring and a full Next.js build succeed;
- durable CI evidence is uploaded even when a later step fails.

V1.5 remains **active** after this feature. It is not release-ready merely because PDF → SVG passes; any later feature still begins with the repository OSS-first/speed gate and the release process remains governed by `AGENTS.md`.
