## Printing

Menu In PDF / Ctrl+P prepares the current working copy, including forms, Typewriter and pending marks, without altering the editable viewer. Choose a page range and 144/216dpi. PDF.js renders the selected pages with print intent; window.print opens the platform print UI (Tauri documentation says this is the cross-platform path: https://docs.rs/tauri/latest/tauri/webview/struct.WebviewWindow.html#method.print ).

The dedicated print container is the only visible content under print media. Named CSS pages use each PDF viewport's dimensions; the container inherits the first named page to avoid an initial default-letter sheet. Actual headless print-to-PDF validates exact page count and portrait/landscape dimensions; no extra blank sheet is accepted. Afterprint frees canvases, document and generated CSS rules. Bounds are 50 pages, 80 million pixels per job, 12 million per canvas; invalid/oversized ranges fail explicitly. This prints raster pages at selected resolution; PDF saving still preserves native text/forms and does not rasterize pages. ## Reader / Tools transfer

Reader's Tools button exports the current working copy and keeps dirty Reader tabs intact. Tools opens an intake page where the user selects an existing operation (merge, repair, info, compress, protect or OCR). The chosen PDF is injected into that operation's **existing** file-input/change path; no engine is invoked automatically. On Tools pages, Open in Reader sends the selected PDF, or the PDF result captured from the normal download action. Non-PDF results are not offered as PDFs. A small module is added to 23 existing PDF-input pages; engine/processing code remains unchanged. The actual merge workflow is tested end to end in browser.

Browser preview uses local IndexedDB, one-use UUID tickets, a 200 MB per-document bound and one-hour expiry; no server/upload. Native apps have separate profiles, so a narrow std::fs inbox under the current user's LocalAppData/SolYan-PDF-Transfer exchanges validated PDF copies using 64-hex tickets and the existing Reader OS-open queue. Tools consumes/deletes its ticket; Reader removes its temporary copy after successful read. Stale inbox copies are cleaned on startup/next transfer. JS cannot supply a filesystem path. Rust tests cover valid UTF-8 names, one-use and traversal rejection; Reader-feature native compilation runs in CI, not locally (no Rust toolchain on this PC).

Both apps must be installed from the same compatible build for Reader-to-Tools intake. The sender waits for receipt and reports an unreceived transfer rather than silently claiming success with an older Tools app. A missing Tools install is checked before writing a transfer. The bundled Reader opens a new Tools window for intake instead of discarding the existing Tools page. Standalone Reader hands off through a separate Tools process; Reader keeps its independent identity and zero sidecars. Native paired-app transfer and old-version upgrade behavior still need installed QA; browser end-to-end success is not a claim those are already proven.
